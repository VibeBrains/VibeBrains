# ЧЕКПОИНТ АГЕНТСКОГО ХОДА — КОНТРАКТ

> **Скопируйте этот файл целиком своей LLM** и попросите собрать чекпоинты хода для своего продукта
> или проверить, что уже собранные читают и пишут снимки одинаково с остальными продуктами набора.
> Модели не нужен интернет и не нужны исходники: всё, что нужно, — здесь и в `testVectors/checkpoint.json`.

---

## 1. ЗАЧЕМ

Агент правит файлы сам, а ещё запускает команды: сборку, форматтер, генератор, `rm`
Чат отслеживает только правки, прошедшие через него
Всё, что изменилось иначе, при откате не вернётся — и откат выглядит завершённым, хотя он неполный

Чекпоинт хода — снимок **всей рабочей папки** в git на границе хода
Откат к чекпоинту возвращает папку целиком, а не только файлы, которые знает чат

Контракт один на VibeIDE и VibeIDEA
Снимок, сделанный одним продуктом, обязан читаться другим: в том же репозитории работают оба

Что здесь определено:

1. Как снимается папка
2. Как называется и подписывается снимок
3. Что лежит в сообщении коммита
4. Когда новый снимок не нужен
5. Как откатывается папка
6. Как убираются старые снимки
7. Что сказать человеку, когда снимка нет

---

## 2. ТЕРМИНЫ

- **Продукт** — программа, делающая снимки: `VibeIDE`, `VibeIDEA`
- **Тред** — одна беседа с агентом в продукте; у неё есть `threadId`
- **Ход** — один заход агента на запрос человека; у него есть порядковый номер `turnIndex`
- **Чекпоинт** — запись в треде, ссылающаяся на снимок
- **Снимок** — коммит git без родителя, дерево которого — вся рабочая папка
- **Id чекпоинта** — sha коммита-снимка (40 или 64 шестнадцатеричных знака)
- **Корень** — результат `git rev-parse --show-toplevel`; снимается весь репозиторий, а не открытая подпапка
- **Живое множество** — id снимков, на которые ссылается хотя бы один тред или журнал продукта

---

## 3. КОГДА СНИМКА НЕТ

Снимок возможен только в git-репозитории и при доступном `git`
Нет репозитория, нет `git` в PATH, репозиторий сломан, git не ответил за отведённое время:

- Чекпоинт создаётся без снимка, **без ошибки** и без уведомления человеку
- Остальная работа чекпоинтов (файлы, которые знает чат) идёт как раньше
- Снимок — страховка сверху, его отсутствие не ломает ход

Отведённое время на команду git задаёт продукт (VibeIDEA — 60 с); истечение считается «git недоступен»

---

## 4. СНИМОК

Снимок не трогает ни настоящий индекс, ни HEAD, ни ветки, ни `git status`
Всё делается через **временный индекс**

Команды (в корне, `git` без оболочки, аргументы массивом):

1. `git rev-parse --show-toplevel` — корень
2. Путь настоящего индекса: `git rev-parse --git-path index`
3. Временный индекс — файл по пути, которого **ещё нет** (в свежем пустом каталоге или с уникальным именем во временной папке)
4. Если настоящий индекс есть — скопировать его во временный; нет (свежий репозиторий) — оставить временный несуществующим
5. С `GIT_INDEX_FILE=<временный индекс>`: `git add -A`
6. С тем же `GIT_INDEX_FILE`: `git write-tree` → sha дерева
7. `git commit-tree <дерево> -m <сообщение>` **без `-p`** — коммит без родителя; подпись из раздела 5; вывод — sha коммита
8. `git update-ref refs/vibe/checkpoints/<sha коммита> <sha коммита>`
9. Временный индекс удалить (всегда, и при ошибке тоже)

Почему именно так:

- `git stash create` **не годится**: он не берёт неотслеживаемые файлы, а вывод сборки и новые файлы терминала — именно они
- Временный индекс не должен быть пустым файлом нулевого размера: git отвергает такой индекс («index file smaller than expected»), и снимки молча не создаются никогда
- Копия настоящего индекса — не мелочь, а разница между пригодным и непригодным: `git add -A` по пустому индексу заново хеширует каждый файл, по копии — только изменившиеся
- Игнорируемые git файлы (`node_modules`, `dist`) в снимок не входят — `add -A` их уважает
- Коммит без родителя: снимок не примыкает ни к одной ветке пользователя и не тянет за собой его историю
- Подмодули попадают как ссылка на коммит, их содержимое снимок не хранит
- `commit.gpgsign` на `commit-tree` не действует (проверено на git 2.54): подписи и запросов пароля нет

Если `write-tree` или `commit-tree` ответили не sha (40 или 64 знака `[0-9a-f]`) — снимка нет, как в разделе 3

## 5. ПОДПИСЬ

Автор и коммиттер задаются **продуктом** через окружение команды `commit-tree`:

```
GIT_AUTHOR_NAME=<Продукт>
GIT_AUTHOR_EMAIL=snapshot@<продукт>.local
GIT_COMMITTER_NAME=<Продукт>
GIT_COMMITTER_EMAIL=snapshot@<продукт>.local
```

`<продукт>` в адресе — имя продукта строчными: `snapshot@vibeide.local`, `snapshot@vibeidea.local`

Зачем:

- `commit-tree` отказывается работать без личности, а в репозитории её может не быть
- `user.name` и `user.email` пользователя на историю снимков не попадают
- Дат не задаём: время снимка — дата коммиттера, её ставит git

---

## 6. ССЫЛКА

`refs/vibe/checkpoints/<sha коммита>`

- Без ссылки снимок — недостижимый объект, и `git gc` его удалит
- Пространство `refs/vibe/` не видно в `git branch`, не уходит `git push` по умолчанию и не пересекается с ветками пользователя
- Id чекпоинта = sha коммита = последний элемент имени ссылки
- Пайплайны и прочие снимки продукта живут в **других** пространствах (`refs/vibe/pipelines/...`): уборка из раздела 10 их не касается

## 7. СООБЩЕНИЕ КОММИТА

### 7.1. Вид

```
<Продукт> checkpoint: ход N (<инструмент|agent>)

tree: <sha дерева>
turnIndex: N
toolName: <инструмент>
threadId: <id треда>
agent: <id агента>
label: <метка>
```

- Первая строка — **тема**: короткая, её показывает `git log --oneline`
- Дальше пустая строка, потом строки `ключ: значение` — по одной на поле, ключ с маленькой буквы, после двоеточия один пробел
- В скобках темы — имя инструмента, после которого сделан снимок; инструмента нет — **слово `agent`**
- Номера хода нет — тема `<Продукт> checkpoint snapshot` (без хода и скобок)
- Завершающего перевода строки в тексте нет (`commit-tree -m` добавит свой)
- `git log refs/vibe/checkpoints/*` читается как история работы агента, а не как столбец одинаковых фраз

### 7.2. Ключи

| Ключ | Обязателен | Значение |
|---|---|---|
| `tree` | да | sha дерева снимка |
| `turnIndex` | нет | порядковый номер хода, целое от 0 |
| `toolName` | нет | имя инструмента, после которого сделан снимок |
| `threadId` | нет | id треда продукта |
| `agent` | нет | id агента: `builtin` для встроенного, для ACP-агента — его id из реестра ACP продукта |
| `label` | нет | метка для ленты, одна строка |

Порядок строк в теле при записи — как в таблице
Время снимка — дата коммиттера, в сообщение не пишется

### 7.3. Запись

- Поле без значения (не задано, пусто или одни пробелы) **не пишется**
- Значение приводится к одной строке: любая серия пробельных знаков, включая переводы строк, — один пробел, края срезаются
- Так в `label` нельзя подложить чужую строку ключа: `шаг\ntree: 000…` записывается как `label: шаг tree: 000…`
- Двоеточие внутри значения остаётся значением
- `turnIndex: 0` — это нулевой ход, а не его отсутствие

### 7.4. Чтение

Читатель берёт поля из сообщения коммита так:

1. Первая строка — тема, в разбор не идёт
2. Остальные строки: срезать края, пустые пропустить
3. Строка вида `ключ: значение` (ключ — латиница и цифры, начинается с буквы; разделитель — первое двоеточие с пробелом) даёт поле
4. **Прежняя запись:** строка `ключ значение` (без двоеточия) тоже даёт поле, но только для известных ключей — так читаются снимки, записанные до контракта
5. Неизвестные ключи читатель **молча пропускает**: контракт может вырасти
6. Ключ повторён — берётся первое вхождение
7. `turnIndex` не целое неотрицательное — поля нет, остальное читается
8. Пустое значение — поля нет

Читатель не падает на сообщении, которого не понял: поля, которых нет, просто отсутствуют

### 7.5. Пример

```
VibeIDE checkpoint: ход 7 (edit_file)

tree: 9f2c7e1d4a6b8035c1e7f90a2b4d6c8e0f1a3b5d
turnIndex: 7
toolName: edit_file
threadId: thread-42
agent: builtin
label: Правка конфигурации
```

## 8. ДЕДУПЛИКАЦИЯ

Ход, ничего не изменивший в папке (агент только читал), не порождает нового коммита

1. Продукт знает id предыдущего снимка этого треда
2. После `write-tree` продукт читает дерево предыдущего снимка: `git rev-parse <предыдущий>^{tree}`
3. Деревья совпали (после среза пробелов, оба непустые) — вернуть **предыдущий** id, нового коммита и новой ссылки нет
4. Предыдущий не читается (сборка мусора, чужая правка ссылок) — писать новый

Зачем:

- Одинаковые снимки подряд превращают историю ходов в шум, где не видно, какой ход что-то сделал
- Дерево того же содержимого даёт тот же sha, поэтому сравнение дешёвое

## 9. ОТКАТ

Откат папки — отдельное действие поверх отката файлов чата, и просто так оно не делается
Он перезаписывает файлы, которых чат не касался, и **удаляет** созданные после снимка

### 9.1. План (ничего не трогая)

1. Файлы снимка: `git ls-tree -r -z --name-only <id>` (в корне)
2. Файлы папки сейчас: `git ls-files -z --cached --others --exclude-standard` — отслеживаемые и неотслеживаемые, **игнорируемые git не входят**
3. Пути читаются по `-z` (разделитель NUL): без него git берёт в кавычки имена с не-ASCII знаками, и такие файлы не находятся на диске
4. `restore` — все пути снимка, отсортированные по кодовым единицам UTF-16, без повторов
5. `delete` — пути папки, которых нет в снимке и которые не игнорируются, отсортированные
6. Игнорируемое (`node_modules`, `dist`, кэши) не удаляется никогда

Человеку показывается, сколько файлов будет удалено; число возвращаемых файлов — это все файлы снимка, а не только изменившиеся

### 9.2. Подтверждение

Откат без явного «да» человека не выполняется
Диалог говорит прямо: папка будет перезаписана состоянием на момент чекпоинта, будет удалено N файлов, отменить это будет нечем
Решение «нет» — ничего не меняется

### 9.3. Выполнение

1. Временный индекс — как в разделе 4 (копия настоящего)
2. С `GIT_INDEX_FILE=<временный>`: `git read-tree <id>`
3. С тем же индексом: `git checkout-index -a -f` — файлы снимка записываются поверх рабочей папки
4. Удалить файлы из `delete` (план вычислен **до** шага 2); уже отсутствующий файл — не ошибка
5. Временный индекс удалить

Настоящий индекс и HEAD не трогаются: после отката `git status` показывает разницу между снимком и коммитом, как до отката
Каталоги, опустевшие после удаления, остаются

### 9.4. Что вернуть вызывающему

Итог — тот же план (`restore`, `delete`): по нему продукт сообщает «восстановлено файлов — X, удалено — Y»

## 10. УБОРКА

Старые снимки снимаются, иначе ссылки копятся вечно

Входы:

- `git for-each-ref --format='%(refname) %(committerdate:unix)' refs/vibe/checkpoints` — строки `refs/vibe/checkpoints/<id> <секунды>`
- Живое множество (раздел 2): объединение состояния окна **и** того, что лежит на диске; другое окно держит свои треды только на диске, своё несохранённое состояние окно знает только само
- Сейчас (`nowMs`)

Правило: снять ссылку, если id **не** в живом множестве **и** её возраст ≥ **1 час** (`nowMs − время снимка ≥ 3 600 000 мс`)

- Свежие снимки щадятся при любом живом множестве: чекпоинт, только что созданный другим окном, мог ещё не дойти до хранилища
- Время в будущем (часы разошлись) — возраст отрицательный, снимок остаётся
- Строки чужих пространств, с пустым id или нечисловым временем при разборе пропускаются
- Снимается только ссылка (`git update-ref -d refs/vibe/checkpoints/<id>`), объекты убирает сам git по своему расписанию
- Ошибка снятия одной ссылки уборку не прерывает; уборка вообще никогда не показывается человеку как сбой
- Живое множество считается заново при каждой уборке, а не копится из событий удаления: пропущенное событие утекает навсегда, пересчёт сам себя исправляет

## 11. ПРЕДУПРЕЖДЕНИЕ О КОМАНДАХ

После отката продукт решает, что сказать человеку

Входы:

- **Есть ли снимок** — у чекпоинта есть id снимка **и** план отката получен
- **Изменит ли откат что-нибудь** — продукт сам решает по плану; неизвестно (`null`) считается «нет»
- **Имена вызванных инструментов** в отрезке сообщений между чекпоинтами, который откатывается (оба края включительно)

Командные инструменты — те, чьи последствия лежат вне слежения чата. Список в `testVectors/checkpoint.json`, ключ `shellToolNames`:

`run_command`, `run_persistent_command`, `run_nl_command`

Сравнение имени **точное**: другой регистр или приставка — не командный инструмент

Решение:

| Есть снимок | Откат что-то изменит | Что показать |
|---|---|---|
| да | да | `restorable` — предложить вернуть папку (раздел 9) |
| да | нет или неизвестно | `complete` — молчать, откат полный |
| нет | — | команд в отрезке нет → `complete`, молчать |
| нет | — | команды были → `uncovered` с числом команд: предупреждение |

Предупреждение при `uncovered` говорит прямо:

- Откат вернул правки чата, но не последствия команд в терминале
- Сколько команд было
- Почему: снять состояние папки на момент чекпоинта было нечем (папка не под git)

Молчание после отката читается как «всё вернулось» — именно этого сбоя контракт и не допускает
Когда снимок есть, команды им покрыты — предупреждение не нужно

## 12. ЧЕГО НЕЛЬЗЯ

- Писать в настоящий индекс, HEAD, ветки; делать `git stash`, `git reset`, `git checkout` над пользовательским состоянием
- Брать личность автора из `user.name` / `user.email` репозитория
- Ставить родителя коммиту-снимку
- Складывать ссылки вне `refs/vibe/checkpoints/` (там действует уборка) — снимки других назначений живут в своих пространствах
- Читать пути без `-z` (имена с не-ASCII знаками ломаются)
- Удалять игнорируемые git файлы при откате
- Откатывать папку без подтверждения человека
- Показывать сбой создания снимка или уборки человеку как ошибку
- Падать на неизвестном ключе или непонятном сообщении снимка

## 13. ПРОВЕРКА: `testVectors/checkpoint.json`

Файл лежит в этом же наборе; оба продукта читают его прямо из набора
Не сид: в `products.json` адресован пустому списку продуктов, в проекты не засевается
Новый случай заводится в векторы, а не в тест одной стороны
Незнакомое поле роняет тест: выросший контракт надо прочитать, а не пропустить

Верхний уровень:

| Ключ | Что |
|---|---|
| `_comment` | описание файла |
| `version` | версия формата вектора, сейчас 1 |
| `pruneMinAgeMs` | порог возраста в уборке, 3 600 000 |
| `shellToolNames` | имена командных инструментов |
| `commitMessage` | сборка сообщения |
| `parseMessage` | разбор сообщения |
| `parsePinned` | разбор вывода `for-each-ref` |
| `staleRefs` | отбор устаревших ссылок |
| `reuse` | решение о переиспользовании снимка |
| `restorePlan` | план отката |
| `coverage` | решение о предупреждении |

Каждая запись любого раздела несёт `name` — человеческое описание случая

| Раздел | Вход | Выход (`expected`) |
|---|---|---|
| `commitMessage` | `product`, `tree`, `meta` {`turnIndex`, `toolName`, `threadId`, `agent`, `label`; все необязательны} | строка сообщения целиком |
| `parseMessage` | `message` | объект с **только** найденными ключами: `tree`, `turnIndex` (число), `toolName`, `threadId`, `agent`, `label` |
| `parsePinned` | `stdout` | массив `{id, committedAtMs}` |
| `staleRefs` | `nowMs`, `pinned` [`{id, committedAtMs}`], `live` [id] | массив id в порядке входа |
| `reuse` | `newTree`, `previousTree` (строка или `null`) | `true` / `false` |
| `restorePlan` | `snapshotPaths`, `workingPaths`, `ignoredPaths` (подмножество `workingPaths`) | `{restore, delete}` — оба списка отсортированы, без повторов |
| `coverage` | `hasSnapshot`, `wouldChangeAnything` (`true`/`false`/`null`), `toolNames` | `{kind: "restorable"\|"complete"}` или `{kind: "uncovered", shellCallCount}` |

Замечание про `restorePlan`: `workingPaths` в векторе — все файлы папки, включая игнорируемые, а `ignoredPaths` — те из них, что игнорирует git
В продукте список папки берётся из `git ls-files --cached --others --exclude-standard`, игнорируемые в нём уже отсутствуют — результат тот же

Проверка готовности продукта:

1. Тест читает файл из набора и прогоняет все разделы чистыми функциями продукта (без git)
2. Отдельная проверка на настоящем временном репозитории: снимок → правка и новый файл в папке → откат → папка равна снимку, `git status` и индекс не изменились
3. Снимок, записанный продуктом, читается разбором соседнего продукта (разбор `parseMessage` на сообщении из `commitMessage`)

## 14. РУЧНАЯ ПРОВЕРКА

В любом репозитории с git, из корня:

```sh
IDX="$(mktemp -u)"
cp "$(git rev-parse --git-path index)" "$IDX"
GIT_INDEX_FILE="$IDX" git add -A
TREE="$(GIT_INDEX_FILE="$IDX" git write-tree)"
COMMIT="$(GIT_AUTHOR_NAME=Product GIT_AUTHOR_EMAIL=snapshot@product.local \
  GIT_COMMITTER_NAME=Product GIT_COMMITTER_EMAIL=snapshot@product.local \
  git commit-tree "$TREE" -m "Product checkpoint: ход 1 (agent)

tree: $TREE
turnIndex: 1")"
git update-ref "refs/vibe/checkpoints/$COMMIT" "$COMMIT"
rm -f "$IDX"
git log --oneline refs/vibe/checkpoints/$COMMIT -1
git status --short   # индекс и дерево — как до снимка
```
