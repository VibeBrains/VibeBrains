# ОСНОВА СЛИЯНИЯ СИДОВ — КОНТРАКТ

> **Скопируйте этот файл целиком своей LLM** и попросите собрать слияние сидов `.vibe` для своего продукта
> или проверить, что уже собранное хранит основу так же, как остальные продукты набора.
> Модели не нужен интернет и не нужны исходники: всё, что нужно, — здесь.

---

## 1. ЗАЧЕМ

Продукт сеет файлы набора в `.vibe/` проекта
Человек правит копию, набор ушёл вперёд — это конфликт сида
Склеить обе правки можно только трёхсторонним слиянием: ваш файл, новая ревизия набора и **основа**
Основа — текст той ревизии, от которой файл был засеян
Без неё не отличить «набор добавил строку» от «вы удалили строку», и слияние сводится к «взять релиз целиком»

Журнал засева хранит только хеши ревизий (`versions.json`, `.defaults.lock.json`)
По хешу текст не восстановить, поэтому текст кладётся рядом, на машине пользователя

Контракт один на VibeIDE и VibeIDEA
Оба сеют один набор в один и тот же `.vibe/`: основа, записанная одним продуктом, обязана читаться другим

## 2. ГДЕ

```
<проект>/.vibe/local/seedBase/<путь сида от .vibe/>
```

- Путь — POSIX, как в манифесте набора: `rules/security.mdc` лежит в `.vibe/local/seedBase/rules/security.mdc`
- Папка `local/` — машинно-локальное, в git не попадает
- Не полагайтесь на то, что корневой `.vibe/.gitignore` уже знает про `local/`: он мог быть создан давно
  Положите в `seedBase/` свой `.gitignore` с одной строкой `*` — звёздочка закрывает и сам этот файл

## 3. ЧТО ЛЕЖИТ В ФАЙЛЕ

- Текст ревизии набора, как набор её отдаёт: UTF-8, переводы строк LF
- Файл на диске с CRLF не повод хранить CRLF: сравнивайте и пишите по LF-нормализованному тексту
- Никаких пометок и заголовков продукта внутри: это копия ревизии, а не рабочий файл

## 4. КОГДА ПИШЕТСЯ

Основа записывается, когда продукт точно знает, что текст на диске или в руках человека — ревизия набора:

1. Файл создан из набора при засеве
2. Нетронутая копия молча обновлена до новой ревизии
3. Копия на диске совпала с нынешней ревизией набора
4. Копия на диске совпала с известной прошлой ревизией (по реестру `versions.json`): тогда её текст и есть основа
5. Человек принял любое решение по файлу — «оставить своё», «взять релиз», ручное слияние:
   он увидел нынешнюю ревизию, она основа следующего слияния

Не пишется для правленого файла, чей текст не совпал ни с одной ревизией: выдумывать основу не из чего

Если текст в файле основы уже тот же — не переписывать
Открытие проекта не должно менять время правки сотен файлов

## 5. ЕСЛИ ОСНОВЫ НЕТ

Проект засеян до того, как продукт начал хранить основу
Продукт **не придумывает** среднюю сторону: слияния трёх сторон нет, есть сравнение двух (ваш файл и релиз)
Окно говорит об этом прямо
Пустая основа допустима, только если окно называет её пустой

## 6. ЧТО СЧИТАТЬ РЕШЕНИЕМ

- Взять релиз: файл записан ревизией набора — как обычный засев, журнал отмечает релиз как принятый
- Оставить своё или ручное слияние: журнал отмечает текущую ревизию набора как разобранную, файл молчит до следующего сдвига набора
- Закрыть окно, ничего не изменив: не решение, файл остаётся в списке

Файл, который человек оставил своим и который набор потом изменил снова, — конфликт, а не «обновить безопасно»
Журнал знает, что на точке сверки файл уже отличался от ревизии: перезапись потеряла бы правки

## 7. ПРОВЕРКА ГОТОВНОСТИ

1. Засейте пустой проект: для каждого сида в `.vibe/local/seedBase/` лежит его копия
2. Измените сид в наборе, отредактируйте копию в проекте: в списке конфликт, а слияние открывает три стороны
3. Удалите `.vibe/local/seedBase/`: слияние сменилось сравнением двух сторон, окно сказало почему
4. `git status` проекта не показывает `.vibe/local/`
5. Оставьте файл своим, поднимите ревизию набора ещё раз: файл снова конфликт
