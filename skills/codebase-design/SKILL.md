# codebase-design

Проектировать **глубокие модули**: много поведения за малым интерфейсом, на чистом шве, проверяемого через этот интерфейс. Цель — рычаг для вызывающих, локальность для сопровождающих и тестируемость для всех.

## Зачем

О структуре кода спорят разными словами про одно и то же — «компонент», «сервис», «граница», «API» — и расходятся, не заметив. Этот навык даёт один набор слов. Его ценность в том, что слова жёсткие: одно понятие — одно слово, без синонимов.

## Словарь

Термины используются ровно так.

**Модуль** (module) — всё, у чего есть интерфейс и реализация. Масштаб любой: функция, класс, пакет, срез через слои. _Не говорить_: юнит, компонент, сервис.

**Интерфейс** (interface) — всё, что вызывающий обязан знать, чтобы пользоваться модулем правильно: сигнатура, но также инварианты, порядок вызовов, виды ошибок, обязательная настройка, поведение по производительности. _Не говорить_: API, сигнатура — они у́же.

**Реализация** (implementation) — то, что внутри модуля. Не то же, что **адаптер**: бывает малый адаптер с большой реализацией и большой адаптер с малой. Об адаптере говорят, когда речь о шве; иначе — о реализации.

**Глубина** (depth) — рычаг на интерфейсе: сколько поведения вызывающий или тест получает на единицу интерфейса, который нужно выучить. Модуль **глубокий**, когда за малым интерфейсом много поведения, и **мелкий**, когда интерфейс почти так же сложен, как реализация.

**Шов** (seam, по Майклу Фезерсу) — место, где поведение можно изменить, не правя код в этом месте; там живёт интерфейс модуля. Где провести шов — отдельное решение, не то же, что «что за ним». _Не говорить_: граница — слово занято ограниченным контекстом из DDD.

**Адаптер** (adapter) — конкретная вещь, которая удовлетворяет интерфейсу на шве. Называет роль, а не содержимое.

**Рычаг** (leverage) — что вызывающие получают от глубины: больше возможностей на единицу выученного интерфейса. Одна реализация окупается на N местах вызова и M тестах.

**Локальность** (locality) — что сопровождающие получают от глубины: изменения, ошибки, знание и проверка собираются в одном месте. Починил раз — починено везде.

## Глубокий и мелкий

**Глубокий модуль** — малый интерфейс и много реализации:

```
┌─────────────────────┐
│   Малый интерфейс   │  ← мало методов, простые параметры
├─────────────────────┤
│                     │
│ Глубокая реализация │  ← сложная логика скрыта
│                     │
└─────────────────────┘
```

**Мелкий модуль** — большой интерфейс и мало реализации (избегать):

```
┌─────────────────────────────────┐
│       Большой интерфейс         │  ← много методов, сложные параметры
├─────────────────────────────────┤
│  Тонкая реализация              │  ← только передаёт дальше
└─────────────────────────────────┘
```

Проектируя интерфейс, спросить: можно ли сократить число методов? упростить параметры? спрятать внутрь больше сложности?

## Принципы

- **Глубина — свойство интерфейса, а не реализации.** Глубокий модуль внутри может состоять из малых, подменяемых частей — они просто не входят в интерфейс. У модуля бывают **внутренние швы** (для его реализации и его собственных тестов) и **внешний шов** на интерфейсе.
- **Проверка удалением.** Представить, что модуля нет. Сложность исчезла — он был передаточным звеном. Сложность появилась заново у N вызывающих — он свой хлеб отрабатывал.
- **Интерфейс — поверхность тестов.** Вызывающие и тесты пересекают один шов. Хочется тестировать **за** интерфейсом — у модуля, скорее всего, не та форма.
- **Один адаптер — шов гипотетический. Два — настоящий.** Шов не вводят, пока через него ничего на деле не меняется.

## Проектировать под тесты

1. **Принимать зависимости, а не создавать их.**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **Возвращать результат, а не производить побочный эффект.**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **Малая поверхность.** Меньше методов — меньше тестов. Меньше параметров — проще подготовка теста.

## Как слова связаны

- У **модуля** ровно один **интерфейс**.
- **Глубина** — свойство **модуля**, измеренное относительно его **интерфейса**.
- **Шов** — место, где живёт **интерфейс** **модуля**.
- **Адаптер** стоит на **шве** и удовлетворяет **интерфейсу**.
- **Глубина** даёт **рычаг** вызывающим и **локальность** сопровождающим.

## Отвергнутые трактовки

- **Глубина как отношение строк реализации к строкам интерфейса** (Оустерхаут): поощряет раздувать реализацию. Здесь глубина — это рычаг.
- **«Интерфейс» как ключевое слово языка или публичные методы класса**: слишком узко — интерфейс включает всё, что вызывающий обязан знать.
- **«Граница»**: занято ограниченным контекстом из DDD. Говорить **шов** или **интерфейс**.
