# Аудит безопасности

Найти в коде то, что атакующий может использовать, и доказать каждую находку.
Навык ничего не правит: результат — отчёт.
Исправление — отдельная задача, и берётся она, только когда о ней попросили.

## Область

Сначала уточнить, что смотрим: весь проект, каталог или дифф ветки.
Не сказано — дифф текущей ветки против основной: там новое, и там же чаще всего новые дыры.

Что ищем, по убыванию цены ошибки:
- Внедрение: SQL, команды оболочки, шаблоны, пути (`../`), десериализация недоверенных данных
- Авторизация: проверка прав на сервере, доступ к чужим объектам по идентификатору, обход через прямой вызов API
- Секреты: ключи и токены в коде, в логах, в сообщениях об ошибках, в ответе клиенту
- Входные данные: валидация на границе, размеры, типы, кодировки
- Сеть: SSRF, открытые редиректы, доверие к заголовкам прокси, TLS без проверки сертификата
- Зависимости: версии с опубликованными уязвимостями — только если в проекте есть способ это проверить (`npm audit`, `pip-audit`, `composer audit`), без выдумок по памяти
- Конфигурация: отладка в проде, CORS `*` с учётными данными, небезопасные куки

## Правила

- **Только чтение.** Не запускать то, что пишет, удаляет, ходит в сеть или трогает окружение. Аудиторы зависимостей — только с разрешения: они ходят в сеть
- **Находка без строки не находка.** Файл, строка, фрагмент кода и путь атаки: откуда приходят данные, куда доходят, что получает атакующий
- **Точность важнее полноты.** Две ложные находки — и отчёт перестают читать целиком. Спорное — в раздел «проверить», а не в находки
- **Не печатать секрет целиком.** Найденный ключ — первые 4 символа и длина, этого хватит, чтобы его найти и отозвать
- **Не дублировать то, что уже ловит проект:** правила линтера безопасности, сканер секретов в CI — назвать, что они есть, и не повторять их вывод
- **Уровень — по последствиям, а не по виду:** внедрение в мёртвом коде — не критично, утечка токена в лог прода — критично

## Порядок

1. Найти границы доверия: где данные приходят извне — HTTP, файлы, очереди, аргументы командной строки, ответы моделей
2. Пройти от каждой границы к опасным местам: запрос к БД, оболочка, файловая система, шаблон, ответ клиенту
3. Для каждого кандидата прочитать код целиком по пути, а не по одной строке: санитайзер может стоять выше
4. Проверить себя: снять только доказуемо ложные находки — те, что опровергаются кодом

## Отчёт

Сначала итог одной строкой: сколько находок какого уровня.
Дальше по находке на блок, от критичных к низким:

```
[критично | высоко | средне | низко] Короткое название
Где: path/to/file.ts:42
Путь атаки: запрос /api/files?name=../../etc/passwd → readFile(join(root, name)) без проверки выхода за root
Что получает атакующий: чтение любого файла, доступного процессу
Как закрыть: одна строка — направление, не патч
```

В конце раздел «Проверить» — места, где доказательства не хватило, с тем, чего не хватило.

## Какая модель

Навык от модели не зависит; модель выбирает роль или пайплайн.
Z.ai называет GLM-5.3 сильной в поиске уязвимостей (CyberGym 84.5%) — это данные самого вендора, независимой проверки нет.
Тариф GLM Coding Plan вендор разрешает только в официальных инструментах: для аудита из IDE надёжнее оплата по токенам.
