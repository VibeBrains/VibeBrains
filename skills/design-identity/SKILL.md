# Дизайн-код и айдентика

Результат должен быть таким, чтобы его можно было **пощупать** и **внедрить**:
Пощупать — HTML-страницы без сервера и сети, открываются двойным кликом
Внедрить — пакеты и генераторы, из которых треки берут код, а не перерисовывают картинки
Картинка без генератора и пакета — это эскиз, а не дизайн-код

Главный принцип — **один источник правды на каждое знание**:
Цвета — один JSON токенов, из него CSS, SCSS, тема UI-библиотеки, TS и брендбук
Геометрия знака — один пакет, из него знак, иконки, favicon и всё, что повторяет форму знака
Брендбук не держит своих цветов и своей геометрии: только импорт

## Шаг 0. Разведка

Прочитать концепт продукта и roadmap всех треков
Выписать:
- аудиторию и её ограничения (зрение, моторика, когнитивная нагрузка, возраст);
- требование доступности (уровень WCAG, экранные чтецы по платформам);
- стеки всех клиентов: от них зависят форматы выхода токенов;
- юридический статус названия (проверка товарного знака, занятость домена, похожие названия в нише).

Название не проверено — знак строится так, чтобы работать без слова
Готово, когда стек каждого трека и уровень доступности названы со ссылкой на файл

Предложить человеку форматы поставки до работы, одной таблицей: что пощупать, что внедрить
Пощупать — страница направлений и кликабельный прототип, внедрить — пакеты
Порядок по умолчанию: страница направлений → одинаковые макеты → главный экран по ролям → прототип → выбор → знак, ассеты, токены, брендбук → компоненты в треках

## Шаг 1. Три направления на выбор

Одна страница `identity/directions.html`, три направления, блоки в одном порядке:
1. Идея и метафора в 2–3 строки
2. Знак: отдельно, со словом, монохром, на тёмном, иконка 1024, 48 и 16 px
3. Палитра светлая и тёмная, у каждой пары «текст/фон» коэффициент контраста
4. Шрифт и шкала на реальных текстах продукта
5. Макеты экранов в HTML/CSS: одинаковый набор и порядок во всех направлениях, главный экран первым, 7–8 экранов по разделам концепта
6. Компоненты с видимым фокусом
Сверху — сводная таблица «характер / сильные стороны / риски», переключатели темы и крупного шрифта, навигация «тот же экран в другом направлении»
Устройство набора экранов, изоляция макетов и кликабельный прототип — [`prototype.md`](prototype.md)

Направления различаются знаком, цветом, шрифтом и формой элементов
Перекраска одного направления в три цвета — это одно направление
Клише ниши (госсиний, медицинский, слащаво-благотворительный) не берутся за основу

Цвета — в одном JSON, контраст считает скрипт по формуле WCAG, провал = код выхода 1
Шрифты — только с открытой лицензией и нужными алфавитами, лицензию и наличие глифов проверить по файлу шрифта
Финал шага — кликабельный прототип из тех же экранов, выбор человек делает по нему
Готово, когда скрипт контраста даёт 0 провалов, сетевых запросов на странице 0, дублей `id` 0, сценарий прототипа зелёный, скриншоты просмотрены глазами

Страница остаётся в репозитории архивом выбора

## Шаг 2. Поставка выбранного направления

Знак из шага 1 — эскиз: его строят заново генератором
Четыре части, две пары агентов можно пустить параллельно при жёстком контракте имён файлов:
- знак и ассеты — [`markGeometry.md`](markGeometry.md), [`assetsPack.md`](assetsPack.md)
- пакет токенов — [`tokensPackage.md`](tokensPackage.md)
- брендбук — [`brandbook.md`](brandbook.md)
Брендбук ссылается на файлы знака по контракту и показывает заглушку, пока их нет: сборка не падает

Элементы интерфейса, повторяющие форму знака (кольцо прогресса, индикатор шагов, лоадер), — [`derivedElements.md`](derivedElements.md)

Готово, когда:
- все проверки обоих пакетов и генератора знака зелёные;
- негативные тесты на сломанной геометрии и сломанном токене падают;
- брендбук собран, без сетевых запросов и ошибок консоли;
- скриншоты светлой, тёмной темы и крупного шрифта просмотрены глазами.

## Шаг 3. Компоненты в треках

Когда в треках появились приложения:
- Storybook на токенах;
- компоненты библиотеки UI (Ionic и т. п.) темизируются переменными из пакета;
- производные элементы знака — компонент поверх функции пакета геометрии.
Подключение пакетов проверяется сборкой настоящего приложения, а не по документации

## Цикл «на глаз»

Человек говорит «кривовато», «неровно», «кажется тоньше» — это данные, а не вкусовщина
1. Измерить: геометрия может быть точной, а восприятие — нет
2. Назвать причины числами: какое отношение, какой зазор, какой центр
3. Не гадать с одной правкой: собрать страницу сравнения поправок в `brand/review/<тема>.html` — каждая поправка отдельно и лучшие сочетания, на рабочих размерах, в обеих темах, с подписью «что поправлено»
4. Выбор человека становится параметрами по умолчанию, прежние значения — архивом в тех же параметрах, страница сравнения остаётся
Каталог причин и поправок — [`markGeometry.md`](markGeometry.md), раздел «Оптика»

## Как работать агентами

- Работу знака, токенов и брендбука ведут субагенты, главный агент принимает по скриншотам и прогону проверок сам
- Субагента ждать в том же ходе, а не отпускать в фон: иначе его отчёт не появится, пока человек сам не напишет
- Два агента, правящих один генератор, — только по очереди
- Доработки страницы направлений — тому же субагенту (продолжение с его контекстом), а не новому
- В брифе субагента: вызовы вне папки проекта — по одному, не параллельно, иначе IDE зависает на запросах разрешений
- Агент пишет в отчёте «посмотрел» только про открытые им картинки, остальное — «проверено замером»
- Снимки, которые субагент не открывал, главный агент открывает сам, выборочно
- Скачанное, инструменты растеризации и скриншоты — в каталог кэша, заданный правилом человека или проекта, в подпапку `<проект>/`
- Каталог не задан — спросить один раз, в репозиторий не класть
- Снимки системным Chrome в headless на macOS вызывали окна разрешений (iCloud, медиатека, тома); причина не установлена — предупредить человека до первого прогона
- Пакеты помечаются `"private": true`: публикация — решение человека
- Коммитит главный агент, после приёмки
