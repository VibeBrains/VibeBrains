# Процесс: от бэклога до выпуска

Пока правки изолированы, параллельная работа агентов идёт сама
Ломается она на пересечениях: две задачи трогают одни файлы, тестер ждёт чужую ветку, дефект находят посреди приёмки
Этот навык задаёт порядок, при котором пересечения видны до начала работы, а не на слиянии

Главный принцип:
Разработка параллельно, приёмка и выпуск — последовательно

## 1. Ветки

- `main` — только выпущенное и его исправления; из `main` можно выпустить в любой момент
- `next` (или `release/<версия>`) — поезд текущего релиза: сюда вливаются принятые задачи
- `task/<id>-<суть>` — ветка одной задачи, ответвляется от `next`, живёт в своём дереве git
- `hotfix/<id>` — исправление выпущенного, ответвляется от `main`

Исправление, сделанное в `main`, сразу вливается в `next` мержем `main → next`, не cherry-pick: история остаётся связной

## 2. Бэклог: карточка задачи

Задача попадает в бэклог карточкой, иначе её нельзя ни спланировать, ни принять:
- **Что** — одна фраза о результате для пользователя
- **Критерии приёмки** — проверяемые пункты: что тестер делает и что видит
- **Зона** — модули, каталоги или файлы, которые задача тронет; оценка, а не обещание
- **Зависимости** — какие задачи должны быть раньше
- **Ресурсы** — нужна ли своя база, порт, сервис, тестовые данные

Карточку без критериев приёмки в релиз не берут: по ней нечего принимать

## 3. План релиза

1. Выбрать задачи в релиз по ценности и зависимостям
2. Составить карту пересечений: строки — задачи, столбцы — зоны
3. Задачи без общих зон идут параллельно
4. Задачи с общей зоной — одно из двух:
   идут последовательно (вторая начинается от ветки, где первая уже влита);
   либо сливаются в одну задачу с одним исполнителем
5. Задача, которая меняет общий контракт (схему базы, API, общий компонент), идёт первой: остальные строятся поверх неё
6. План записать в файл релиза (`docs/releases/<версия>.md` или раздел roadmap): состав, порядок, кто принимает

Пересечение, найденное на слиянии, стоит дороже пересечения, найденного на плане: поэтому карта — до первой строки кода

## 4. Параллельная работа: дерево git и свои ресурсы

На каждую задачу — своё дерево git (`git worktree add ../wt/<id> -b task/<id> next`)
Тогда тестер принимает одну задачу, пока агент пишет другую, и никто не видит чужой недоделки

Дерево делит с соседями всё, что не в git, поэтому задаче выделяется слот ресурсов:
- **Порт** — базовый порт плюс номер слота (`3000 + слот`), и так для каждого сервиса
- **База** — своя база или схема на слот (`app_slot3`), заполненная из сида, а не из чужой копии
- **Окружение** — свой `.env` копией с поправленными портами и именами баз
- **Контейнеры** — имя проекта compose с суффиксом слота (`-p app-slot3`), чтобы стенды не гасили друг друга
- **Зависимости** — ссылка или копия `node_modules`, без установки в общую папку

Слоты учитывать в одном файле (`slots.md` или `.vibe/local/slots.json`): задача, слот, дерево, кто занял
Задача принята или брошена — стенд гасится, слот освобождается, дерево удаляется

## 5. Приёмка

- Тестер принимает в дереве задачи, на её стенде, по критериям из карточки
- Итог один из двух: **принято** или **возврат** с шагами воспроизведения и тем, что ожидалось
- «Принято с замечаниями» не бывает: замечание — либо возврат, либо новая карточка в бэклог
- Одновременно в приёмке может быть несколько задач, но в ветку релиза они вливаются по одной (раздел 6)

## 6. Вливание в поезд

1. Принятая задача вливается в `next`
2. После каждого вливания — полный прогон проверок проекта на `next`: типы, линт, тесты
3. Следующая принятая задача сначала подтягивает свежий `next` в свою ветку, прогоняет проверки и только потом вливается
4. Конфликт разрешает исполнитель задачи, которая вливается второй: он знает свою правку
5. Красный `next` останавливает вливания, пока не позеленеет

## 7. Дефект на приёмке: куда он идёт

Первый вопрос — откуда дефект:

- **Внесён задачей этого релиза** — возврат в ветку этой задачи, правка там же, переприёмка
- **Был и раньше, но блокирует приёмку** (не работает главная кнопка меню, вход, навигация — полный прогон невозможен):
  это блокер; `hotfix/<id>` от `main`, отдельная короткая приёмка;
  вливается в `main` (выпускается сразу, если задет выпущенный продукт) и тут же мержем `main → next`;
  приёмка релиза продолжается, когда исправление пришло в `next`
- **Был и раньше и не блокирует** — карточка в бэклог, в следующий релиз; текущий релиз его не ждёт

Чинить старый дефект «прямо тут же» в ветке задачи нельзя: правка уедет вместе с задачей, и если задачу вернут, исправление вернётся вместе с ней

Решение «блокер или нет» принимает тот, кто ведёт релиз, а не исполнитель: исполнитель склонен чинить всё, что видит

## 8. Выпуск

1. В `next` только принятые и влитые задачи, проверки зелёные
2. Регрессионный прогон на собранном артефакте, а не на дереве разработки
3. `next → main`, тег, публикация
4. Следующий релиз уже набран по плану: его задачи можно было начинать параллельно, но в `next` они попадают только после выпуска текущего

Один релиз в приёмке одновременно: два поезда на одной ветке — это снова пересечения, только позже

## 9. Роли агентов

Процесс программируется ролями, а не одним агентом:
- **Планировщик** — карточки, карта пересечений, план релиза (сильная модель)
- **Исполнитель** — одна задача в своём дереве (дешёвая или средняя модель)
- **Рецензент** — дифф задачи против карточки, до приёмки (модель другого семейства)
- **Тестер** — критерии приёмки на стенде задачи, итог «принято / возврат»
- **Ведущий релиза** — человек: решает, что блокер, и даёт «выпускаем»

В VibeIDE:
Роли и пайплайны — `.vibe/roles.json` и `.vibe/pipelines.json` (пайплайн `feature`)
Своё дерево для роли — настройка `vibeide.subagent.worktree`
Независимые шаги одной волной — метка `wave` в пайплайне

## Чего не делать

- Не брать задачу в работу без карточки с критериями приёмки
- Не вливать в `next` непринятое «чтобы тестер посмотрел»: смотрят в дереве задачи
- Не давать двум задачам один слот ресурсов
- Не выпускать из `next` непринятое «по пути» вместе с хотфиксом: хотфикс идёт от `main`
- Не чинить чужой старый дефект внутри ветки задачи
