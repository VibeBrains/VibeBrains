# Ревью на упрощение

Ошибки и упрощение — два разных ревью
Смешанные, они друг другу мешают: важная ошибка тонет среди «можно короче», а правка ради красоты прячет поломку
Поэтому сначала ревью на ошибки (`review-pr`), потом этот проход — по уже правильному коду

## Что искать

Только в новом и изменённом коде:
- **Повтор существующего.** Новый хелпер, константа или проверка уже есть в проекте — найти поиском и назвать файл
- **Абстракция без второго вызова.** Обёртка вокруг одного вызова, интерфейс с одной реализацией, параметр, который всегда один
- **Мёртвое.** Неиспользуемые импорты, ветки, которые не достижимы, закомментированный код, флаг, который никто не меняет
- **Лишняя работа.** Повторный проход по тому же списку, чтение файла дважды, вычисление в цикле, которое не зависит от цикла
- **Длинный путь к простому.** Пять строк там, где стандартная функция языка или проекта делает то же одной

## Чего не делать

- Не искать ошибки: их нашёл предыдущий проход; заметил явную — одной строкой в конце, отдельно
- Не менять поведение: упрощение, после которого код делает другое, — это не упрощение
- Не спорить о вкусе: «я бы назвал иначе» — не находка
- Не предлагать абстракцию «на будущее»

## Формат находки

Файл и строка — что лишнее — чем заменить (конкретно, с путём к существующему коду, если это повтор)
Находок нет — так и написать, не выдумывать ради объёма
