# Внешний исполнитель бригадира

Часть навыка `brigadier`: его описание, включение и выключение — в `../SKILL.md`, а здесь подключение и запуск исполнителя
Триггеры раздела: «подключи DeepSeek», «внешний исполнитель», «дешёвый исполнитель», «отдай работу DeepSeek», «worker.sh», «бригадир не видит исполнителя», «добавь провайдера для бригадира», «обнови цены», «цены DeepSeek устарели», «засей ключ», «импортируй ключ»

## Что это

Бригадир отдаёт часть работы отдельному неинтерактивному `claude -p`
У этого процесса, и только у него, сервер подменён на API провайдера: адрес, ключ и модели идут через его окружение
Главная сессия остаётся на подписке Claude и ничего не знает о ключе провайдера
Нет ключа или навык не подключён — бригадир работает по прежней лестнице моделей, ничего не ломается

Запуск: `bash <каталог исполнителя>/worker.sh …` (бит исполнения при копировании может потеряться); на Windows — `powershell -File <каталог исполнителя>\worker.ps1 …`
Каталог исполнителя: `~/.claude/skills/brigadier/worker/` или `.vibe/skills/brigadier/worker/` проекта
В примерах ниже `worker.sh` — это эта команда целиком

Файлы исполнителя:
- `worker.sh` — macOS и Linux
- `worker.ps1` — Windows (не прогнан: на машине автора нет PowerShell)
- `providers/<имя>.json` — профиль провайдера; сейчас `deepseek.json`

## Что нужно заранее

- Claude Code: команда `claude` в терминале
- macOS и Linux: `bash` и `python3` — скрипт разбирает ими профиль и ответ `claude`
- Linux: `secret-tool` (пакет `libsecret-tools`) — или ключ в переменной `BRIGADIER_WORKER_<ПРОВАЙДЕР>_KEY`
- Windows: PowerShell 5.1 или новее
- Ключ провайдера и пополненный баланс; для проб хватит пары долларов

## Откуда запускать

Из любого каталога: скрипт находит профили провайдеров рядом с собой, а не в текущей папке
Вызывать полным путём: `bash ~/.claude/skills/brigadier/worker/worker.sh check deepseek`
Каталог, где исполнитель работает, задаёт `--dir`, а не текущая папка

## Подключение

1. Получить ключ у провайдера
   DeepSeek: `https://platform.deepseek.com/api_keys`, ключ создаётся в кабинете, пополнить баланс
2. Положить ключ в хранилище секретов командой навыка
   macOS и Linux: `worker.sh set-key deepseek`
   Windows: `worker.ps1 set-key deepseek`
   Ключ вводится в приглашении, не в аргументе: в списке процессов и в истории оболочки его нет
   macOS кладёт его в связку под именем `brigadier-worker-deepseek` (`security`), Linux — в `secret-tool` (пакет `libsecret-tools`), Windows — в Credential Manager
   Запасной путь без хранилища — переменная окружения `BRIGADIER_WORKER_DEEPSEEK_KEY`
   Ключ уже лежит в `.env` или переменной — вместо ввода см. «Ключ уже есть» ниже
3. Проверить: `worker.sh check deepseek`
   Код 0 — ключ найден и сервер ответил на короткий запрос; код 1 — причина строкой в stderr, ключ в вывод не попадает
4. Первый пробный запуск на безопасной задаче:
   ```
   echo 'Перечисли файлы верхнего уровня и одной строкой скажи, что это за проект' | \
     worker.sh run --provider deepseek --tier cheap --effort low --mode read --dir <репозиторий> --brief -
   ```
   В конце вывода — итог, токены, модель и уровень; строка про тот же запуск ложится в журнал
5. Сравнить на одной своей задаче: отдать её исполнителю и своей дешёвой модели, сверить результат и цену
   Выбор «кому что» бригадир делает по журналу и этому сравнению, а не по умолчанию

### Ключ уже есть

Ключ лежит в переменной окружения или в `.env`, и вводить его заново не нужно: `worker.sh import-key deepseek` (Windows: `worker.ps1 import-key deepseek`)
Команда сама кладёт ключ в то же хранилище, что и `set-key`, и сразу выполняет `check`
Имя переменной, под которой ключ обычно лежит, берётся из поля `keyEnv` профиля (у DeepSeek `DEEPSEEK_API_KEY`)

Источники, в этом порядке:
- переменная окружения `keyEnv`
- файл `~/.vibe/.env`
- старая запись хранилища `brigadir-worker-<провайдер>` (см. «Переход с прежней версии»)
- файл из `--from-file <путь>` (Windows: `-FromFile`): если задан, смотрится только он

В `.env` разбираются строки `KEY=value` и `export KEY=value`, кавычки снимаются, комментарии пропускаются

Поведение:
- Один источник со значением, или одинаковые значения в нескольких — ключ кладётся в хранилище, в ответе назван источник и хранилище, значения нет
- Несколько разных значений — команда ничего не пишет, перечисляет источники (путь и имя переменной, без значений), код 1; нужный файл указывается через `--from-file`, а ключ из старой записи хранилища — через `--from-legacy` (Windows: `-FromLegacy`)
- Ни одного — код 1, подсказка про `set-key`

Значение идёт в хранилище не через аргументы процессов: на macOS через stdin `security -i`, на Linux через stdin `secret-tool`, на Windows через память процесса

## Переход с прежней версии

Раньше навык звался `vneshniy-ispolnitel`, запись в хранилище — `brigadir-worker-<провайдер>`, переменные — `BRIGADIR_WORKER*`, каталог журнала — `brigadir-worker`
Ключ под старым именем молча не читается: `check` и `run` говорят «найден ключ под старым именем — выполни import-key»
`import-key <провайдер>` берёт ключ и из старой записи хранилища (значения в выводе нет), кладёт под новое имя и выполняет `check`
Старую запись после этого удаляет владелец: macOS — `security delete-generic-password -s brigadir-worker-<провайдер>`
Старые переменные окружения `BRIGADIR_WORKER*` не читаются: переименовать на `BRIGADIER_WORKER*`
Старый журнал не переносится сам: перенести файл `runs.jsonl` в новый каталог

## Как запускать

`worker.sh run` с параметрами:

| Параметр | Что |
|---|---|
| `--provider` | имя профиля, например `deepseek` |
| `--tier` | `cheap` или `strong`: модель берётся из профиля |
| `--effort` | уровень рассуждения из списка профиля; бригадир выбирает его по задаче, `max` разрешён |
| `--mode` | `read` — чтение и поиск; `write` — ещё и правка файлов, в отдельном worktree |
| `--dir` | каталог, в котором работает исполнитель |
| `--base` | режим write: ref, от которого создаётся worktree и ветка (`origin/dev`, тег, коммит); по умолчанию `HEAD` (Windows: `-Base`) |
| `--budget` | необязателен: ручное переопределение потолка цены запуска в настоящих долларах провайдера; по умолчанию потолок — `maxRunUsd` профиля |
| `--brief` | файл с брифом или `-` для stdin |
| `--bash-allow "<шаблон>"` | дополнительная разрешённая команда, например `"cargo test*"`; можно повторять |

Выход: 0 — успех, 2 — упёрся в потолок цены, 1 — ошибка

### Потолок цены

Потолок — предохранитель от зацикливания, а не бюджет задачи: его не выбирают под каждый запуск
По умолчанию это `maxRunUsd` профиля (у DeepSeek 2 доллара); `--budget` (Windows: `-Budget`) заменяет его вручную, например для пробы обрыва
`--budget` в `claude` не передаётся: счётчик самого `claude` считает по ценам Claude и обрывает DeepSeek в ~30 раз раньше, чем набежит реальная цена
Поэтому скрипт запускает `claude -p --output-format stream-json --verbose`, читает события построчно и считает цену сам в настоящих долларах провайдера по `prices` профиля
Вход считается точно: по `usage` каждого сообщения ассистента (сообщение учитывается один раз, кэш отдельно)
Выход считается оценкой: `usage` потока отдаёт `output_tokens=0`, поэтому берётся длина текста и вызовов инструментов, делённая на `CHARS_PER_TOKEN` (2.5), плюс оценка размышлений из событий `thinking_tokens`
Цена пересчитывается после каждого такого события; выше потолка — процесс останавливается (SIGTERM, через `KILL_GRACE_SEC` секунд SIGKILL; на Windows сразу `taskkill /T /F`), итог «упёрся в бюджет», код 2
Точность: вход приходит с каждым сообщением целиком, поэтому факт может превысить потолок на стоимость одного запроса
Обрыв в середине ответа считается по оценке выхода; если событие `result` успело прийти, стоимость и токены точные, иначе в выводе стоит «~» и пометка «оценка»
`claudeCounterUsd` в журнале — счётчик `claude` из итогового события, только для справки; у оборванного запуска его нет (`null`)
Профиль без `prices` — потолок не считается, запуск идёт, в выводе строка «потолок не считается: в профиле нет цен»
Профиль без `maxRunUsd` и без `--budget` — запуск без потолка, в выводе строка «потолок не задан»

При обрыве и при любом неуспешном итоге возвращается сделанное:
- режим write — как обычно: коммит в ветку worktree, дифф и stat
- режим read — последний текстовый ответ исполнителя из потока с пометкой «частичный результат»
- в выводе и журнале `verdict` «упёрся в бюджет» и `partial: true`
Уровень рассуждения у DeepSeek фактически low, high или max: остальные значения провайдер сводит к ближайшему

### Признак чтения по кругу

Вход за запуск выше `READ_LOOP_INPUT_TOKENS` (2 000 000 токенов), а вызова записи (`Edit`, `Write`, `MultiEdit`) не было ни одного — в конце вывода строка «внимание: … признак чтения по кругу», в журнале поле `readLoop: true`
Это не обрыв и не ошибка: запуск идёт до конца, потолок цены считается отдельно
Сигнал бригадиру: бриф слишком широкий или исполнитель перечитывает одно и то же — следующий запуск узкий и по уже сделанному
Порог — именованная константа рядом с остальными: `READ_LOOP_INPUT_TOKENS` в `worker.sh`, `$ReadLoopInputTokens` в `worker.ps1`

### Режим write — всегда в отдельном worktree

Основное дерево репозитория скрипт не трогает (обойти — `--allow-main-tree`, без причины не нужно)
`--dir` — основное дерево git-репозитория: скрипт сам делает `git worktree add` во временный каталог (`$BRIGADIER_WORKER_WORKTREES`, по умолчанию `<tmp>/brigadier-worktrees`) на ветке `brigadier/<время>` от `--base` (по умолчанию HEAD)
Базу задавать явно, когда основное дерево стоит на чужой фича-ветке: `--base origin/dev` (Windows: `-Base origin/dev`)
`--dir` уже worktree: исполнитель работает в нём как раньше, ничего не создаётся
`--dir` не в git-репозитории: отказ
Правки исполнителя скрипт коммитит в ветку worktree одним коммитом «brigadier: <первая строка брифа>», без атрибуции
В конце вывода: путь worktree, ветка, `git diff --stat`, путь файла с полным диффом (`<worktree>.diff`), команды влить и убрать
Worktree скрипт не удаляет
Порядок бригадира:
1. `worker.sh run … --mode write --dir <основное дерево>`
2. Приёмка: дифф из файла или `git -C <worktree> diff <база> HEAD`, проверки проекта в worktree
3. Принял — `git merge <ветка>` (или cherry-pick) и уборка командой из вывода; не принял — только уборка
4. Пушит бригадир: исполнитель коммитить и пушить сам не может

### Бриф

Исполнитель запускается с `--bare`: он не читает `CLAUDE.md`, правила, навыки и хуки
Всё нужное несёт бриф: цель, пути, контракт, язык ответа и комментариев, что не трогать, команды проверок, что вернуть
Секреты (ключи, токены, пароли, `.env`) и чужие данные в бриф и в каталог исполнителя не попадают: всё, что он читает, уходит провайдеру
Код, в том числе приватных репозиториев, отдавать можно; проект закрывается для исполнителя только строкой «Исполнитель: выкл» в проектном правиле `brigadier`

## Исполнитель не удаляет файлы

`rm` в режиме write запрещён, на Windows — ещё `del` и `Remove-Item`: удалить файл исполнитель не может
Лишние файлы (`__probe.tmp`, пустые заготовки, случайный `.env`) он перечисляет в отчёте, а удаляет бригадир при приёмке или в уборке worktree
В бриф: «`.env` не создавай, головы миграций проверяй по файлам» — пустой `.env` ради `alembic heads` тоже мусор

## Журнал

Одна JSON-строка на запуск: время, провайдер, ступень, модель, уровень, режим, каталог, токены, `costUsd`, `costExact`, `capUsd`, `claudeCounterUsd`, секунды, итог, `partial`, `readLoop`
`costUsd` — реальная стоимость по ценам профиля (`null`, если в профиле нет `prices`), `costExact` — точная она или оценка (оборванный запуск), `capUsd` — действовавший потолок, `claudeCounterUsd` — счётчик `claude`, только для справки, `readLoop` — вход перевалил порог без единого вызова записи (признак чтения по кругу)
Текста брифа в журнале нет
Путь, по приоритету: переменная окружения `BRIGADIER_WORKER_LOG`, затем поле `logFile` профиля провайдера (`~` раскрывается), затем `~/.cache/brigadier-worker/runs.jsonl` (на Windows `%LOCALAPPDATA%\brigadier-worker\runs.jsonl`)
На машине владельца `logFile` стоит в личной копии профиля: `/Volumes/Storage/Caches/brigadier/runs.jsonl`; в поставляемом профиле поля нет

## Обновить цены

Триггеры: «обнови цены», «цены DeepSeek устарели»; `check` печатает «цены проверены N дней назад — обнови», когда `pricesCheckedAt` старше 30 дней
Цены лежат только в профиле (`providers/<имя>.json`, блок `prices`), нигде больше их не дублировать: в доках — ссылка на профиль
Порядок:
1. Открыть страницу из `pricesSource` профиля
2. Сверить имена моделей ступеней и цены за 1M токенов: вход при промахе кэша (`inputMiss`), вход при попадании (`inputHit`), выход (`output`)
3. Поправить в профиле только `prices` и `pricesCheckedAt`; считаем по пиковому тарифу (верхняя оценка), это записано в `pricesNote`
4. Скопировать профиль во все копии навыка (`~/.vibe/skills/…`, `~/.claude/skills/…`, общий набор VibeBrains)
5. Прогнать `worker.sh check deepseek` (предупреждения быть не должно) и пробный запуск чтения; по желанию сверить `costUsd` с расходом в кабинете провайдера

Цены профиля: `providers/deepseek.json`
Профиль без `prices` не ломает запуск: стоимость в выводе «неизвестна», `costUsd` в журнале `null`

## Другой провайдер

Любой сервер, который понимает Anthropic Messages API и принимает токен в `ANTHROPIC_AUTH_TOKEN`
Профиль кладётся в `~/.config/brigadier-worker/providers/<имя>.json` (Windows — `%APPDATA%\brigadier-worker\providers`, каталог меняет `BRIGADIER_WORKER_PROVIDERS`); он перекрывает одноимённый поставляемый
Образец — `providers/deepseek.json`:

| Поле | Что |
|---|---|
| `baseUrl` | адрес Anthropic-совместимого API |
| `secret.service`, `secret.env` | имя записи в хранилище и запасная переменная окружения |
| `tiers.cheap.model`, `tiers.strong.model` | модели ступеней |
| `efforts`, `defaultEffort` | допустимые уровни рассуждения |
| `maxRunUsd` | потолок цены одного запуска в долларах по умолчанию, страховка от зацикливания; нужны `prices` |
| `logFile` | путь журнала запусков, необязателен; переменная `BRIGADIER_WORKER_LOG` сильнее |
| `worktreesDir` | каталог worktree режима write, необязателен; переменная `BRIGADIER_WORKER_WORKTREES` сильнее; по умолчанию временный каталог. Исполнитель собирает проект внутри своей копии, поэтому каталог — на диске, где не жалко места |
| `extraEnv` | дополнительные переменные процесса исполнителя, не секретные |
| `prices`, `pricesSource`, `pricesCheckedAt`, `pricesNote` | цены за 1M токенов по моделям, откуда взяты, дата сверки (необязательны) |

После профиля — `set-key`, `check`, пробный запуск, как выше

## Узкие места

Проверено на DeepSeek 27.10.2026, `claude` 2.1.286:

- Счётчик `claude` не знает модели DeepSeek и считает по запасным ценам Claude, поэтому завышен в десятки раз (замер: реальные $0.0317 при счётчике $0.7211)
  `--max-budget-usd` в `claude` поэтому не передаётся: он обрывал запуск при реальной цене в ~30 раз ниже заданной
  Потолок считается самим скриптом по потоку `stream-json` и ценам профиля, см. «Потолок цены»; счётчик остаётся в выводе как `claudeCounterUsd` для справки
- В потоке `stream-json` `usage` сообщения ассистента повторяется в каждом его блоке и не накопительный: вход суммируется по `id` сообщения; `output_tokens` там 0, точный выход только в итоговом `result`
- `--bare` берёт токен из `ANTHROPIC_AUTH_TOKEN` — подтверждено запуском; связку Claude (OAuth) и `CLAUDE.md` не читает
- Ограничение инструментов — список разрешённых команд и запрет остальных (`--permission-mode dontAsk`), а не песочница
  Режим read не даёт правок и записи, но защитой от враждебного кода репозитория служит только отдельный каталог
  Субагенты и сеть (`WebFetch`, `WebSearch`) у исполнителя запрещены, `git commit` и `git push` тоже
- Процесс исполнителя помечен `BRIGADIER_WORKER=1`: правило бригадира по этой переменной знает, что оно исполнитель, и никому не раздаёт
- Ступени «средняя» у DeepSeek нет: `strong` — это `deepseek-v4-pro`, `cheap` — `deepseek-flash`
- Скрипты требуют `python3` (разбор JSON) и `curl` (для `check`)
- Ключ не передаётся ни в аргументах `claude`, ни в аргументах `curl`: заголовок идёт в `curl` конфигом через stdin
