# save-session — бесшовная передача состояния между сессиями

## Зачем

Контекст сессии живёт только внутри неё. Этот скилл выгружает рабочее состояние в
**хендофф-файл** в памяти проекта так, чтобы следующая сессия по слову «продолжи»
восстановила его целиком — как будто разрыва не было.

Хендоффов может быть **несколько параллельно** (каждый — отдельная фича/поток, как если бы
разные субагенты вели свои задачи). «Общий продолжи» собирает все открытые хендоффы, строит
единую картину и продолжает работу уже с пониманием всего сразу.

## Где хранится

- Каталог памяти этой сессии — назван в системном промпте («You have a persistent
  file-based memory at …»). Обозначим его `<MEM>`.
- Хендоффы — в подпапке `<MEM>/sessions/<slug>.md` (по одному файлу на поток).
  `<slug>` — короткий kebab-case по теме потока (`neon-theme`, `prod-deploy`, `ru-i18n`).
- Индекс открытых потоков — секция в `<MEM>/MEMORY.md` (грузится каждой сессией, поэтому
  следующая сессия сразу видит, что есть незавершённое):

  ```
  ## ⏸ Открытые сессии (скажи «продолжи», чтобы возобновить)
  - [neon-theme](sessions/neon-theme.md) — ⏳ ждёт: перекрасить админку — 2026-07-23
  - [prod-deploy](sessions/prod-deploy.md) — 🚧 в работе: настроить cron бэкапов — 2026-07-23
  ```

## Определение режима

По формулировке пользователя и наличию хендоффов:

1. **SAVE** — просьба сохраниться/прерваться. Записать/обновить хендофф текущего потока.
2. **RESUME один** — «продолжи» и либо открыт ровно один поток, либо назван конкретный
   (`продолжи neon-theme`). Возобновить его.
3. **RESUME общий** — «продолжи»/«собери сессии»/«общий продолжи» и открытых потоков
   несколько без указания конкретного. Собрать ВСЕ, синтезировать, продолжить целостно.

Если режим неоднозначен — кратко показать список открытых потоков и уточнить одним вопросом.

## Протокол SAVE

1. **Определить slug потока.** Явно назван пользователем (`сохранись как neon-theme`) —
   взять его. Иначе вывести короткий устойчивый slug из доминирующей задачи потока. Если
   хендофф с близкой темой уже есть — **обновить его**, не плодить дубль.
2. **Собрать состояние** (см. шаблон ниже) — не по памяти, а фактом: текущая ветка и
   последний коммит (`git`), запущенные сервисы/порты, незакоммиченные правки
   (`git status`), точный следующий шаг.
3. **Записать** `<MEM>/sessions/<slug>.md` по шаблону (Write создаёт подпапку сам).
   Шапка шаблона обязательна целиком, с первой строки файла `---` и с `status: open`.
   Хендофф без шапки движок не видит: он не объявится в начале сессии, и «продолжи» его не найдёт.
   Так и было 12.11.2026: файл записан заголовком `# …` без шапки, а в отчёте стояло «сохранил».
3а. **Проверить, что хендофф виден** — до отчёта, фактом:
   `head -1 <файл>` — ровно `---`, и `grep -n "status: open" <файл>` находит строку
   Проект под VibeMemory — ещё вызвать `handoff_list` (MCP vibememory): `<slug>` должен быть в списке
   Не прошло — исправить файл и проверить снова; без пройденной проверки слово «сохранил» в отчёт не пишется
4. **Обновить индекс** — добавить/обновить строку потока в секции «⏸ Открытые сессии»
   в `MEMORY.md` (создать секцию, если её нет). Статус-эмодзи: 🚧 в работе, ⏳ ждёт
   решения пользователя, 🧪 на проверке, 🔴 заблокировано.
   **Исключение — проекты под VibeMemory** (память лежит в `~/.vibememory/store/projects/…`,
   а слаги в `~/.claude/projects/` — симлинки туда): там `MEMORY.md` ГЕНЕРИРУЕТСЯ движком
   из верхнеуровневых записей, и дописанная строка стирается при первом синке. Шаг
   пропустить: открытые хендоффы движок находит сам по `status: open` и объявляет их в
   начале следующей сессии. Проверено 10.09.2026.
5. **Зафиксировать сделанное** (глобальное правило «фиксация сделанного»): если в проекте
   ведётся `docs/roadmap.md` — отметить завершённые пункты; нетривиальные грабли/решения —
   в `docs/knowledge/<домен>/` со строкой в индексе. Нет таких доков — пропустить, хендофф
   самодостаточен.
6. **Отчитаться**: какой поток сохранён, где файл, какой следующий шаг записан, сколько
   всего открытых потоков.

## Шаблон файла хендоффа

```markdown
---
name: session-<slug>
description: "⏸ Хендофф потока «<тема>»: <где остановились в одну строку>"
metadata:
  type: project
  status: open        # open | done
  updated: <YYYY-MM-DD>
---

# Поток: <тема>

**Статус:** 🚧/⏳/🧪/🔴 — <одна фраза>
**Ветка / последний коммит:** <branch> @ <hash> «<subject>»

## Готово, когда
<финишная черта: что должно быть правдой и чем это проверить — команда, тест, страница>

## Следующий шаг (первое, что делать при возобновлении)
<конкретное действие, с которого продолжить — команда/файл/строка>

## Что уже сделано
- <пункт> (коммит <hash> / файл path:line)
- …

## Осталось сделать
- [ ] <шаг>
- [ ] <шаг>

## Открытые вопросы / развилки (ждут пользователя)
- <вопрос и варианты, если есть>

## Решения
- <решение одной строкой>
  (при закрытии потока к каждой строке дописывается отметка, см. «Закрытие выполненного потока»)

## Контекст и грабли (чего нет в коде)
- <подводный камень, который иначе потеряется>

## Навыки для возобновления
- <навык> — <зачем он понадобится на следующем шаге>

## Состояние окружения
- Запущено: <сервисы, порты, dev-серверы>
- Незакоммиченные правки: <есть/нет, что именно>
- Проверка: <команды, которыми убедиться, что всё цело>
```

## Протокол RESUME (один поток)

1. Прочитать `<MEM>/sessions/<slug>.md`.
2. Кратко (3–5 строк) доложить: тема, статус, следующий шаг — чтобы пользователь увидел,
   что контекст восстановлен.
3. Свериться с фактическим состоянием: та же ветка? сервисы подняты? правки на месте?
   Разошлось — сказать и подстроиться.
4. Сверить сделанное с «Готово, когда»: черта уже пройдена — закрыть поток, а не делать лишнее.
   После сжатия контекста движок сам подаёт открытые хендоффы целиком — опора там, а не в пересказе истории.
5. **Продолжить с «Следующего шага».** Не начинать заново, не переспрашивать то, что уже
   решено в хендоффе.
6. Когда поток полностью завершён — **закрыть** (см. ниже).

## Протокол RESUME общий (собрать все потоки)

1. Прочитать **все** `<MEM>/sessions/*.md` со `status: open`.
   Список движка в начале сессии — не весь: сверить его с `ls <MEM>/sessions/`
   Файл без шапки (первая строка не `---`) — потерянный хендофф: дописать шапку по шаблону и взять в работу
2. Построить единую картину: по каждому потоку — тема, статус, следующий шаг. Найти
   пересечения и конфликты (два потока трогают один файл/зону; один блокирует другой).
3. Выдать **сводку** пользователю: список потоков + предлагаемый общий план (в каком
   порядке, что можно объединить, где риск конфликта).
4. Дальше действовать целостно — не как набор изолированных задач, а как одна работа со
   знанием всех потоков. По завершении каждого — закрывать его.

## Закрытие выполненного потока

Поток доделан — не удалять молча:
1. Сверить с «Готово, когда»: каждая строка черты подтверждена фактом — командой, тестом, страницей
2. Разобрать раздел «Решения»: каждой строке дописать, куда решение ушло
   `→ память <имя>`, `→ knowledge <путь>`, `→ правило <id>`, `→ навык <имя>` или `→ локально`
   Локально — решение нужно было только этой задаче и дальше не живёт
   Без разбора хендофф закрывать нельзя: решения иначе остаются в закрытом файле, и их никто не прочтёт
   Движок это проверяет: `vibememory doctor` предупреждает о закрытом хендоффе с решением без отметки
3. В его файле выставить `status: done` и дописать итог одной строкой.
4. Убрать строку потока из секции «⏸ Открытые сессии» в `MEMORY.md` (секцию удалить, если
   потоков не осталось).
5. Файл оставить в `sessions/` как след (или перенести в `sessions/done/` — по желанию
   пользователя). В отчёте назвать, что закрыто.

## Гигиена

- Один поток = один файл = один slug. Обновлять существующий, не плодить копии.
- Хендофф пишется **фактом**: ветку/коммит/порты сверять командами, не воспроизводить по
  памяти (глобальное правило самопроверки).
- Секретов в хендофф не писать — только имена/пути и указатели, где взять.
- Что уже записано в спеке, коммите, issue или knowledge — не пересказывать, а ставить ссылку: путь, хеш, адрес.
  Хендофф несёт только то, чего нигде больше нет.
- `MEMORY.md` — только индекс (строка на поток); содержимое хендоффа живёт в его файле.
- Слишком старый `done`-хендофф пользователь снесёт сам; сам их не чищу без просьбы.
